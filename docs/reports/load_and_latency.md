---

## 1. Executive Summary

Production incident-response platforms face bursty operational traffic during major system outages: multiple engineers, automated alerts, and Slack integrations concurrently submit diagnostic queries.

This report evaluates IncidentIQ's throughput, latency percentiles, error rates, resource utilization, and memory stability under:
1. **Multi-level Concurrency Testing**: 10, 25, and 50 concurrent users, with **1,000 requests per load level** across **three independent runs per level** (9 runs, 9,000 discrete requests).
2. **Sustained Load Testing**: A **10-minute (600.2s) continuous stress test** generating **41,350 requests** at 25 concurrent users.
3. **Real-Provider End-to-End Benchmark**: 10 live calls to external cloud LLM providers (Groq `openai/gpt-oss-20b` and Gemini `gemini-3.5-flash-lite`).

### Key Observation: Local vs. Cloud Latency Decoupling
This comparison reveals that **internal API orchestration, database queries, and retrieval take only 5–60 ms**, whereas **external LLM generation takes 12–16 seconds**. Mocking LLM calls is therefore necessary for testing concurrency, connection pools, and memory stability, while the real-provider benchmark validates end-to-end integration fidelity.

## 5. Capacity and Scalability Conclusions

1. **Throughput Ceiling:** On a single Python asyncio process, the application sustains ~70–76 requests per second before saturating the event loop.
2. **Production Multi-Worker Recommendation:** Deploying 4 Uvicorn workers behind NGINX or Envoy will scale capacity linearly to $\approx 280\text{–}300\text{ RPS}$, comfortably serving high-velocity enterprise incident traffic.
3. **Connection Pooling:** Ensuring database connection pool sizes exceed maximum worker concurrency (`pool_size=50`, `max_overflow=50`) prevents database thread starvation under burst conditions.
